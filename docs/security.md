# Local service security

Use the API on a local loopback binding. Demo tokens use a server-held HMAC secret with a maximum one-hour lifetime. Issue them through the local CLI and keep them out of logs and source files. There is no public token creation endpoint. Both finance and prediction routes bind data access to the signed tenant. Explicitly targeting another tenant returns 403. Extra body fields are rejected and queries bind SQL parameters.

The local identity mechanism has no revocation, external identity integration, or per-user roles. Authenticated requests are rate-limited per tenant within the API process with `CLAIMS_REQUESTS_PER_MINUTE`, default 120. A multi-instance deployment would need a shared limiter. Structured request logs contain request ID, HTTP method, status, and elapsed time. Prompt checks catch explicit cases covered by evaluation. Tenant isolation relies on the identity and database query filters. It does not depend on the prompt. The live provider adapter has a request timeout and does not receive ledger rows.

OIDC mode validates an RS256 access token using the configured HTTPS JWKS, issuer, and audience. The verified token must carry an integer tenant and the claims:read scope. The API rejects wrong issuers, audiences, expired tokens, absent scopes and tenant changes. The local integration test generates temporary private material and serves only its public key as a JWKS fixture. Demo mode remains available for Docker smoke tests. See [deployment](deployment.md) for configuring a real issuer.

The newer serving-image audit checked 22 installed Python distributions with zero known findings. The separate Python 3.14 CPU environment uses filelock 4.2.4 and setuptools 84.2.1. The audit enumerated 82 installed distributions and reported zero findings among those matched. The exact torch 2.15.0+cpu variant was skipped by the PyPI advisory lookup. A separate OSV query returned zero advisories for upstream torch 2.15.0. Container operating-system packages were outside this dependency audit.

The local identity harness imports fictional tenant users into a real Keycloak realm and generates its own development CA. FastAPI validates the signed token and requires the `claims-analyst` realm role as well as `claims:read`. Keycloak emits the RFC 9068 access-token header type. The test uses separate clients to exercise invalid audience, absent scope, and expiry. The API never receives the fictional users' passwords.
